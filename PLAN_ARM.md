# PLAN_ARM.md — учётная часть ИС «АРМ-Монитор» (отдельно от карты)

Источник требований — курсовой проект «ИС для управления АРМ в СФР»
(главы 1.3, 2.1, 2.2). Модель данных берётся **из Т-модели курсового
(табл. 2.3, 2.5, 2.6) без отступлений**: ВКР должна совпадать с тем, что уже
защищено. Карта (чертёж, `floor_plans` / `wall_*` / `workspaces`) в этом плане
не трогается; стык с ней описан в Этапе 9 и делается последним.

Общие правила — в `CLAUDE.md`. Каждый этап — отдельный коммит.

## Этап 1. Схема БД учётной части

18 таблиц по табл. 2.6 (+ `audit_log`, см. ниже): `department`, `employee`, `building`, `room`,
`workplace`, `equipment_type`, `manufacturer`, `equipment_model`,
`operating_system`, `equipment`, `assignment`, `ticket`, `ticket_work`,
`inventory`, `inventory_result`, `writeoff_act`, `role`, `app_user`.

- Типы — по доменам D1–D13 (табл. 2.5): `INTEGER`, `VARCHAR(20/50/150/255)`,
  `TEXT`, `NUMERIC(12,2)`, `NUMERIC(8,2)`, `SMALLINT`, `BOOLEAN`, `BYTEA`.
- Составные PK там, где они в модели: `assignment(equipment_id, assigned_at)`,
  `ticket_work(ticket_id, work_no)`, `inventory_result(inventory_id, equipment_id)`.
- AK: `equipment.inventory_no`, `app_user.login`, `app_user.employee_id`,
  `writeoff_act.equipment_id`.
- CHECK для перечислений (значения в БД — латиницей, подписи — на клиенте):
  - статус оборудования: `in_stock` «На складе», `in_use` «В эксплуатации»,
    `in_repair` «В ремонте», `pending_writeoff` «К списанию», `written_off` «Списано»;
  - вид операции назначения: `assign`, `move`, `return`;
  - тип заявки: `install`, `move`, `service`, `repair`;
  - приоритет: `low`, `normal`, `high`;
  - статус заявки: `new`, `in_progress`, `done`, `rejected`, `closed`;
  - статус инвентаризации: `open`, `closed`;
  - вид расхождения: `missing`, `wrong_room`, `extra`;
  - статус согласования акта: `draft`, `on_approval`, `approved`, `rejected`.
- 19-я таблица сверх Т-модели — `audit_log` (журнал действий из BPMN
  «Администрирование»): `log_id` PK, `occurred_at TIMESTAMP`, `user_id` FK →
  `app_user` (NULL для неудачного входа), `action VARCHAR(50)`
  (`login`, `login_failed`, `create`, `update`, `delete`, `status_change`, …),
  `entity VARCHAR(50)`, `entity_id VARCHAR(50)`, `details TEXT` (JSON
  изменённых полей). Запись — из сервисов, в той же транзакции, что и
  само действие. ER-модель курсового пока не меняется.
- Одна миграция Alembic поверх существующих; таблицы карты не трогать.
- `backend/app/seed.py` — роли (5 шт.), администратор, демо-справочники и
  10–20 единиц оборудования, чтобы было что показывать.

**Приёмка.** `alembic upgrade head` на чистой БД и `downgrade -1` проходят;
DDL совпадает с табл. 2.3/2.6 (сверить вручную по списку столбцов).

## Этап 2. Авторизация и роли

- `POST /api/v1/auth/login` → JWT (access); пароль — `bcrypt` напрямую
  (`passlib` не сопровождается и конфликтует с `bcrypt` 4.x), секрет и время
  жизни — из `.env`. Роль в токен не кладётся — читается из БД на каждом
  запросе, поэтому блокировка и смена роли действуют сразу.
- Маршруты карты (`/floor-plans`) пока открыты — закрываются при встраивании
  (этап 9).
- Зависимости FastAPI: `get_current_user`, `require_roles(...)`.
- Матрица прав — табл. 1.2, в одном месте (`core/permissions.py`):

| Роль | Код |
|---|---|
| Администратор ИС | `admin` |
| Системный администратор | `sysadmin` |
| Начальник отдела | `head` |
| Руководитель подразделения | `dept_head` |
| Сотрудник | `employee` |

- `dept_head` и `employee` видят только своё подразделение / своё оборудование —
  фильтр на уровне сервиса, а не только скрытием кнопок на клиенте.
- Администрирование: CRUD `app_user`, назначение роли, блокировка
  (`is_active`), `last_login_at` обновляется при входе.

- Просмотр журнала действий (`GET /audit-log`, фильтры: пользователь,
  период, сущность) — только `admin`.

**Приёмка.** Без токена — 401, с чужой ролью — 403; тест на матрицу прав
(pytest, по одному запросу на роль × защищённый маршрут).

## Этап 3. Справочники

CRUD для 9 справочников: подразделения (иерархия через `parent_id`),
сотрудники (признак МОЛ), здания, помещения, рабочие места, типы
(срок службы), производители, модели, ОС (признак отечественной).

- Единый шаблон: `GET` список с поиском и пагинацией, `GET /{id}`,
  `POST`, `PUT`, `DELETE`.
- Удаление при наличии ссылок → 409 с перечнем, кем занята запись
  (шлюз «Есть ссылки на запись?» из BPMN 2.4).
- Pydantic: `*Create` / `*Update` / `*Read`, как в существующем `floor_plan`.

**Приёмка.** pytest: создать → найти → изменить → удалить; удаление
используемой модели даёт 409.

## Этап 4. Реестр оборудования (А1)

- `POST /equipment` — постановка на учёт: проверка уникальности
  инвентарного номера, статус принудительно `in_stock`.
- Список с фильтрами: статус, тип, подразделение, помещение, МОЛ, ОС,
  «истекает срок службы» (дата ввода + срок типа).
- Карточка: характеристики + история назначений + заявки + инвентаризации.
- Сделано: регистрация, правка, список с фильтрами и областью видимости по
  роли, карточка с историей, `GET /equipment/summary`. **Отложено:** паспорт
  PDF — нужен файл кириллического шрифта в репозитории.
- Паспорт АРМ — PDF (`reportlab`; шрифт с кириллицей, например DejaVu Sans,
  положить в репозиторий и зарегистрировать — встроенные шрифты кириллицу
  не выводят).
- Изменение статуса **только через сервисы этапов 5–8**, прямой `PUT status`
  запрещён — иначе история и акты разойдутся с реестром.

**Приёмка.** Повтор инвентарного номера — 409; паспорт скачивается и
содержит все поля карточки.

## Этап 5. Назначение и перемещение (А2)

**Сделано** (`POST /equipment/{id}/assignments`, кнопки в карточке). Отличие
от исходного плана: МОЛ при выдаче **не меняется** — это бухгалтерская
ответственность; сотрудник из назначения — «пользователь» (holder), он видит
выданное ему оборудование наравне с тем, где он МОЛ. Акт приёма-передачи
PDF отложен вместе с паспортом (нужен кириллический шрифт).

`services/assignment_service.py` — одна транзакция:
запись в `assignment` → обновление `equipment.workplace_id`, `mol_id`,
`status = in_use` (или `in_stock` при возврате).

- Проверки: оборудование не `written_off` / `pending_writeoff`;
  рабочее место существует.
- Акт приёма-передачи — PDF.
- Заявки типа `install` / `move` из этапа 6 закрываются назначением.
- Нет свободного оборудования → ответ с признаком «нужна закупка»
  (фиксируется в ИС, без интеграции с закупками).

**Приёмка.** После перемещения история содержит обе записи в хронологии,
текущее место в карточке — новое.

## Этап 6. Заявки и журнал работ (А3)

**Сделано** (`/tickets`, экраны «Заявки» и карточка заявки, кнопка «Подать
заявку» в карточке оборудования). Уточнения к плану: ремонт при взятии в
работу переводит технику в «В ремонте», при выполнении — обратно; комментарий
к переходу (причина отклонения, итог) пишется записью журнала работ; заявки
`install`/`move` закрываются вручную — автосвязь с назначением не сделана.

- Создание заявки сотрудником — только на своё закреплённое оборудование
  (или без оборудования для `install`).
- Конечный автомат статусов в одном месте, недопустимый переход → 409:
  `new → in_progress | rejected`, `in_progress → done`,
  `done → closed` (подтверждение заявителем) | `in_progress` (возврат).
- `ticket_work` — записи журнала с автонумерацией `work_no` в пределах заявки.
- Результат диагностики «не ремонтопригодно» → оборудование
  `pending_writeoff` и черновик акта списания (этап 8).
- Уведомления: лента «мои заявки» со статусами; без почты.

**Приёмка.** pytest на все допустимые и пару недопустимых переходов.

## Этап 6.1. Кабинет сотрудника и просмотр карты (сделано)

- «Мой профиль» (`GET /profile`) — стартовая страница сотрудника: ФИО,
  должность, отдел, руководитель, территория (здание, кабинет, РМ — по
  выданной технике), техника на АРМ, число открытых заявок.
- Руководитель — новое поле `department.head_employee_id` (миграция
  `3aa18ca7867a`), выбирается в справочнике подразделений.
- Отдельная страница `#/tickets/new`: тип → техника карточками → срочность →
  описание. Модальное окно заявки удалено.
- `#/map` — просмотр сохранённых планов без редактирования (режим `view` в
  `FloorPlanCanvas`), редактор карты — по ссылке для `manage_catalogs`.
  Демо-план 3 этажа в seed. Клиент карты ходит на `/api/v1` через прокси Vite.
- Сотруднику и руководителю подразделения справочники в меню не показываются.

## Этап 7. Инвентаризация (А4)

- Создание: подразделение (или всё Отделение) + основание.
- Опись формируется по реестру: строка `inventory_result` на каждую единицу
  в помещениях подразделения, `is_present = false` по умолчанию.
- Отметки: наличие, фактическое помещение; вид расхождения вычисляется
  (`missing` / `wrong_room`), найденное вне описи — `extra`.
- Ведомость расхождений и итоговый акт — PDF/Excel.
- Закрытие: по выбору — скорректировать размещение (через сервис этапа 5)
  и/или отправить отсутствующее в списание; после `closed` правки запрещены.

**Приёмка.** Опись из 5 единиц, 1 отсутствует, 1 в чужом помещении →
в ведомости ровно 2 строки с верными видами.

## Этап 8. Списание (А5) и отчёты

**Списание.** `draft → on_approval → approved | rejected` (согласует только
`head`). `approved` → статус `written_off`, `workplace_id = NULL`
(«освободить рабочее место»); `rejected` → обратно `in_stock`.
Выгрузка акта для 1С:БГУ — CSV/XML-файл.

**Отчёты** (6 видов из гл. 2.1): состав парка по подразделениям; истекающий
срок службы; распределение по ОС; статистика заявок по исполнителям и
срокам; результаты инвентаризаций; списанное за период. Каждый — JSON для
экрана + экспорт `xlsx` (`openpyxl`) и PDF.

**Приёмка.** Числа отчёта «по подразделениям» совпадают с `SELECT count(*)`
по seed-данным.

## Этап F. Клиент учётной части

Ведётся параллельно с этапами 3–8 (экран на этап), когда готов API этапа.

- Чистый TypeScript без UI-фреймворка, как и карта (`strict`, без `any`).
  Экран — класс с `mount(container)` / `unmount()`, по образцу классов сцены.
- Общий минимум, написанный один раз: hash-роутер (`#/equipment/12`),
  генератор таблицы (колонки, сортировка, пагинация), генератор формы по
  описанию полей с выводом ошибок валидации из ответа API, модальное окно.
- Отдельная точка входа (`admin.html` в том же Vite-проекте), карта не
  импортируется — при встраивании станет ещё одним экраном.
- Экраны: вход; справочники; реестр + карточка; назначение; заявки
  (сотрудник / исполнитель); инвентаризация; списание и согласование; отчёты;
  пользователи.
- Меню и кнопки — по роли из токена; сервер всё равно проверяет права.
- Клиент API — по образцу `frontend/src/api/floorPlans.ts`
  (сообщения об ошибках по коду ответа).
- Место под схему в «Назначении» — заглушка-список рабочих мест помещения.

## Этап 9. Стык с картой (позже, отдельной постановкой)

Сейчас только зафиксировать, чтобы не пришлось переделывать:

- `room` ↔ `floor_plans`: в курсовом план помещения — `room.plan BYTEA`.
  При встраивании добавляется `room.floor_plan_id` (FK); `BYTEA` остаётся
  для подложки.
- `workplace` ↔ `workspaces`: учётное «рабочее место» становится единственной
  сущностью; геометрия (`x, y` + ширина/высота/поворот карты) — в `workplace`,
  таблица `workspaces` мигрирует в неё.
- Статус места на карте (`free` / `occupied`) **вычисляется** из наличия
  оборудования в статусе `in_use`; `reserved` — отдельный признак. Хранить
  статус вторым источником нельзя — разойдётся с реестром.
- Клик по месту на карте → карточка оборудования (вариант «Работа с
  интерактивной схемой» расширяет «Назначение и перемещение»).

## Принятые решения

- Стек: FastAPI, SQLAlchemy + PostgreSQL, клиент на чистом TypeScript.
- PDF: `reportlab`.
- Журнал действий: таблица `audit_log` в БД (этап 1).

**Расхождения с курсовым, которые позже поправить в ВКР:**
гл. 1.3 — React → TypeScript + Vite; ER/KB/FA/Т-модели — нет `audit_log`
(19 сущностей вместо 18); у `department` — `head_employee_id` (руководитель); у `role` добавлен `code VARCHAR(20)` (AK) —
машинный код роли для проверки прав, наименование остаётся для людей.
